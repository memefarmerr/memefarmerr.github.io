# hosting/archive

The update archive, in the layout a static host serves and apt expects:

```text
dists/couchbox/InRelease                    signed metadata
dists/couchbox/Release                      the same, unsigned
dists/couchbox/main/binary-amd64/Packages   the index apt reads
pool/main/c/couchbox-shell/...              the packages themselves
```

Nothing in here is edited by hand. It is generated by `scripts/build-archive.sh` (m10-03), which
packages the repository with `dpkg-deb`, builds the indexes with `apt-ftparchive`, and signs them
with the project's key on the build machine:

```bash
sudo ./scripts/build-archive.sh --sign 039BC3F8DCF336D7381C3A4EFCAD8F1A2114DE7B
```

It is committed so that pushing the commit is publishing the folder: the Pages workflow uploads
`hosting/` as it stands. It is regenerated rather than patched, because the value of the archive is
that it is the product of a commit.

The signing key is kept outside this repository and never reaches the workflow: the private half
belongs in secure storage, and the fingerprint is in `docs/updating.md`. Without `--sign` the
archive is complete and unsigned, the script ends by saying it is not publishable, and apt refuses
it, which is the correct behaviour rather than a bug.

To try the whole path with no network and one machine:

```bash
cd hosting/archive && python3 -m http.server 8080
# then point /etc/couchbox/update-channel at http://127.0.0.1:8080 on the machine
# being tested, and run apt update there
```

The design of the channel, the key, and how a person removes it is in
`docs/updating.md`.
