# hosting

Everything that gets published to the project's website and to the update archive
lives here, so that what is uploaded is what is in the repository rather than
something assembled by hand from four places at the last minute.

This folder is named `hosting` rather than `build` on purpose. `build/` already
means the image `scripts/build.sh` produces, it is ignored by git, and
`scripts/clean.sh` deletes it.

## what is here

| path | what it is | committed |
| --- | --- | --- |
| `index.html` | the download page, and the first of the three warnings in ADR-0028 | yes |
| `archive/` | the update archive, as it will be uploaded: `dists/` and `pool/` | yes, and regenerated rather than edited |
| `.nojekyll` | tells GitHub Pages to serve every file as it is, which a package archive depends on | yes |

## the site, and how it is published

The live site is the project's GitHub user site, `https://memefarmerr.github.io/`,
published from its own repository. The contents of this folder are copied into
that repository: `index.html` at its root, `archive/` and `.nojekyll` beside it.

That is the whole publishing step: copy what is here into the site repository
and push. Nothing in this repository can deploy into the user site by itself,
and no credential is kept around to try: the copy is deliberate, and what gets
copied is visible in a commit.

The image does **not** go here. It is about a gigabyte, and a static site has a
size and a bandwidth allowance to respect; a tagged release's assets are built
for files that size. The page links to the release.

## before publishing

One placeholder has to be replaced in `index.html`:

- `REPLACE-WITH-RELEASES-URL`, with the release that carries the ISO

The archive is signed before it is committed (see below). Publishing an unsigned
archive would make every machine that has the channel refuse it, which is the
correct behaviour and a poor release.

## the archive, and what is deliberately not here

`archive/` is generated by `scripts/build-archive.sh` from the repository, with
`dpkg-deb` for the package and `apt-ftparchive` for the indexes. It holds
Couchbox's own packages only, never a mirror of Debian.

It is committed rather than ignored, which is unusual for generated files and
deliberate: this folder exists to be uploaded, a clone that produces an empty
archive folder cannot be published, and whoever publishes a release should be
able to see exactly what that release carried. It is a package of a few hundred
kilobytes, not an image. Regenerate it with the script rather than editing it by
hand: what matters is that the published archive is the product of a commit.

Sign it with the project's key before committing:

```bash
sudo ./scripts/build-archive.sh --sign 039BC3F8DCF336D7381C3A4EFCAD8F1A2114DE7B
```

The signing key is not here and never will be: the private half belongs in
secure storage outside this repository, the same rule the repository already
applies to secrets. The public half travels to machines in the image, at
`/usr/share/keyrings/couchbox-archive-keyring.gpg`. Until the indexes are
signed, apt refuses the archive, which is the correct behaviour rather than a
bug to work around.

## trying the page locally

```bash
cd hosting && python3 -m http.server 8000
```

That is also how a test update channel is served, which is how the whole update
path can be tried with no network and one machine.
